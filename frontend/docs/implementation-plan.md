# Implementation plan: HVAC Warranty demo

Source of truth: [Demo workflows.md](Demo%20workflows.md). Rules: [../CLAUDE.md](../CLAUDE.md), which in short says the
visual design is frozen and new screens are built only from existing components and classes.

Items marked **🔍 REVIEW** need your sign-off before they're built.

---

## 1. Principles

- **One app, role-aware routes.** Admin, dealer/distributor and customer share the existing `AppShell`. `/` renders the
  right home page for the role (A01, DL01 or CU02). Shared screens (units, complaints) are one page each, and the
  server decides which rows come back.
- **The server scopes data; the UI only hides.** `RequireRole` blocks routes, `permissions.ts` hides actions, and the
  demo server filters every response by the caller.
- **Phone layout for customers.** The existing shell is already responsive: the sidebar becomes a drawer below `lg`,
  and `DataTable` turns rows into cards below `md`. Customer pages wrap content in `mx-auto max-w-xl`, the class
  already used by the registration success card, so they read as a phone screen on any device. The shell itself
  doesn't change.
- **Shared state across windows.** Every window talks to one demo server. Lists and the bell refetch on window focus
  and poll every 5 seconds, so the Admin window sees a customer's complaint without a manual refresh.

## 5. Domain model, roles and scoping (Phase 1)

### Roles

`Role = "admin" | "dealer" | "distributor" | "customer"`. This replaces technician, distributor (old meaning),
claims_agent and service_center.

| Role        | Sees (enforced by the server)                                  | Can do                                                                                                    |
| ----------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| admin       | Everything                                                     | Everything, including approve/reject registrations, void, send to service, claim actions, simulate, reset |
| distributor | Units, registrations, complaints and claims of all its dealers | Register units and bulk import for a chosen dealer, raise complaints; read-only claims                    |
| dealer      | Only its own units, registrations, complaints and claims       | Register units, bulk import, raise complaints for its customers; read-only claims                         |
| customer    | Only their own units and complaints                            | Self-register (pending approval), raise complaints, download certificates                                 |

Changes: `types/domain.ts` (`Role`), `lib/permissions.ts` (new permission list such as `units:void`,
`registrations:review`, `complaints:send`, `claims:act` and `simulate:run`), `nav-items.ts` (menus per role, section
6), `app/router.tsx` (`RequireRole` per route), `transitions.ts` (claim state machine), and the login page (seed
accounts replace the mock role picker when the demo server is used).

Menus by role:

- **Admin:** Dashboard, Registrations, Units, Models, Complaints, Claims, Admin (Dealers & users, Integration log,
  Simulate).
- **Dealer and distributor:** Home, Register a unit, Bulk import, My sold units, Complaints & claims.
- **Customer:** My units, Register a product, Complaints.

### Business logic (pure functions in `src/lib`, used by both the server and the UI, with unit tests)

- `partWarranty(part, today)` returns status and daysRemaining. End = start + months. Expiring soon is 30 days or
  fewer. Void wins. The end day counts as covered.
- `unitParts(model, unit)` attaches the parts from the model template when a unit is created.
- `replacePart(unit, partType, newSerial, date)` closes the old part and starts the new one's warranty on `date`.
- `entitlement(unit, parts, today)`: void or no active covered part gives Chargeable/Chargeable and no claim.
  Otherwise parts are Covered if any affected part is active and `coversParts`, and labour is Covered only if the UNIT
  part is active and `coversLabour`. For the seed unit AER-SPL15-210311 this gives compressor parts Covered, labour
  Chargeable.
- `validateRegistrationRow(row, master, existingSerials)` returns per-field errors: unknown model, duplicate serial,
  missing install date.
- `claimTransitions` (Draft → Submitted → Approved → Paid; Submitted → Rejected), with roles, in the
  `transitions.ts` pattern.
- `scope(user, rows)` for the server's row filters.

## 6. Shared demo server (Phase 1)

| Topic             | Approach                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Location          | `demo-server/` at the repo root (next to `frontend/`), its own `package.json`, TypeScript run with `tsx`.                                                                                                                                                                                                                                                                                                                                             |
| Framework         | **Express** plus `multer` for uploads, `exceljs` (xlsx read and template), `pdfkit` (certificate PDF) and `qrcode` (QR SVG). These are all server-side, so the frontend gets no new dependencies except the scanner (3.4).                                                                                                                                                                                                                            |
| Store             | In-memory store seeded from `demo-server/src/seed.ts`, saved to `demo-server/data/state.json` after every write so a restart keeps demo state. **Reset demo data** reloads the seed. No SQLite: native builds on Windows are a setup risk.                                                                                                                                                                                                            |
| Reusing MSW logic | Endpoint shapes stay the ones in `src/mocks/handlers.ts` (`Paginated<T>`, `ApiErrorBody`, `/auth/*`, `/claims/:id/transitions`).
